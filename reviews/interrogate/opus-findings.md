### 1. [critical] The documentation window shows "This page could not be displayed" after a live scheme switch while it is closed
**Location**: `src/manic/ui/documentation_viewer.py:416-444` (`_check_painted`, `_on_painted`, `_on_paint_timeout`), `:454-461` (`_on_theme_changed`), `:463-466` (`open`)
**Finding**: The paint check stops only when `self.web_view.isHidden()` is true. Closing the dialog hides the top-level window, but the web view's own hidden flag stays false. A closed window runs no animation frames, so `manicPainted` never becomes true. `_on_theme_changed` reloads the current page even when the window is closed. The 50 ms poll then runs for 20 s, the 10 s timeout reloads once, and the second timeout calls `_show_status(..., retry=True)`, which hides the web view. `open()` does not reload a page that failed, so the user reopens Documentation to an error page for a page that loads fine.
**Evidence**: `docs_scheme_probe.py` opens the docs, waits 4 s (the page draws, `is_rendered()` is True), closes the window, switches to dark, then waits 25 s. Result: 313 `_check_painted` calls, 3 timeouts, 1 reload, status "This page could not be displayed.", Retry shown. After reopening and waiting 3 s it still shows the error and `is_rendered()` is False. Closing the window within 150 ms of opening, before the first draw, gives the same result without a scheme switch (`docs_probe.py ... 150`). The control (close after the page drew, no switch) stays rendered. Following the OS scheme live is a headline feature of this branch, so a user who opened the docs once and then reaches sunset hits this. Retry recovers it, but the app reports a failure that did not happen and polls in the background for 20 s.
**Suggestion**: Gate polling and the timeout on whether the dialog is visible (`self.isVisible()`), not on `web_view.isHidden()`. In `_on_theme_changed`, skip the reload while the window is closed and mark the page stale. In `open()`/`showEvent`, reload when `not self.is_rendered()`. Add a test: open, close, switch scheme, reopen, assert `is_rendered()`.

### 2. [warning] Double-clicking a Summary chart to enlarge it replaces the grid's selection
**Location**: `src/manic/ui/chart_style.py:278-281` (`BarRows.eventFilter`, `MouseButtonRelease`), wired to `MainWindow._on_qc_sample_activated` → `GraphView.select_sample` → `select_only_plot` (`graphs.py:714-721`)
**Finding**: The enlarge button's tooltip says "Enlarge (or double-click the chart)". The first click of a double-click delivers Press and Release before the DblClick event, and `BarRows` activates the row on that Release. `select_sample` calls `select_only_plot`, so the user's multi-selection collapses to the row under the pointer before the popup opens. This click-to-select on the abundance and ratio charts is new on this branch; on `main` only the Identity chart did it.
**Evidence**: `dclick_probe.py` selects Bio_001..003, then sends click + double-click to a Peak area row. The popup opens, and the selection changes from `['Bio_001', 'Bio_002', 'Bio_003']` to `['Bio_001']`. Each activation also runs the full summary rebuild in finding 3.
**Suggestion**: Activate on release only when no double-click follows. Defer the activation by `QApplication.doubleClickInterval()` and cancel it on DblClick, or drop double-click-to-enlarge, since the enlarge button already exists. Add a test that sends the real click + double-click sequence.

### 3. [warning] A selection click re-integrates every sample and rebuilds the Summary charts it only needs to re-highlight
**Location**: `src/manic/ui/main_window.py:1708-1719` (`on_plot_selection_changed`), `:1513-1548` (`_update_total_abundance`)
**Finding**: The comment says "Verdicts do not depend on the selection; the charts only re-highlight". The code calls `_refresh_mode_charts(..., skip_qc=True)`, which re-reads the EICs, re-integrates every sample (`update_ratios`), and rebuilds the abundance chart's series and axes. Only after that does it call the `set_highlighted` methods this branch added. Those calls are the only part a selection change needs.
**Evidence**: `sel_probe.py` (labelled bench data, 30 samples, Pyruvate) measures `_refresh_mode_charts(skip_qc=True)` at 161 ms and 166 ms. `set_highlighted` on both charts takes 0.1 ms. A full plot click takes 194 ms. `main` also rebuilt on selection, so the cost is old, but this branch made the rebuild the highlight path and wrote a comment that says otherwise. Every rebuild also restarts `BarRows.refresh()` and the axis and name fitting.
**Suggestion**: In `on_plot_selection_changed`, call `set_highlighted(selected)` on the three charts and drop the `_refresh_mode_charts` call. That deletes a moving part and removes about 165 ms from every click. If something depends on the selection-scoped recompute, name it in the code.

### 4. [warning] `settings_window.py` goes from 919 to 1063 lines; `main_window.py` and `graphs.py` grow further past the limit
**Location**: `src/manic/ui/settings_window.py` (919 → 1063), `main_window.py` (2837 → 3023), `graphs.py` (2012 → 2112), `integration_window_widget.py` (1115 → 1263), `documentation_viewer.py` (739 → 976)

**Evidence**: Line counts come from `git show origin/main:<f> | wc -l` against the working tree. The panel logic reads five QSettings keys and three widget states, and it is the most stateful new code in the window. Keeping it inline in a 3k-line class makes it hard to test on its own; it is tested only through a full `MainWindow`.
**Suggestion**: Move each settings page into a `settings_pages/` module, or at least move `DeconvolutionPage` out. Extract the panel layout (splitter, the two toggle actions, width persistence, the roomy/fits rules) into a small `PanelLayout` object that `MainWindow` owns, and move the menu builders next to it.

### 6. [nit] `MainWindow._show_no_samples` calls the charts' private `_clear_chart`
**Location**: `src/manic/ui/main_window.py:1412-1420` (also `_update_total_abundance`, `self.summary.total_abundance._clear_chart()`)
**Finding**: The window clears two charts through a private method and the third through public `clear()`. The three Summary charts share one role (clear, update, highlight, `sample_activated`) but have no shared public surface, so the window lists them by hand in three places (`setup_ui` wiring, `_show_no_samples`, `_update_total_abundance` highlight).
**Suggestion**: Give the three widgets a public `clear()` and let `SummaryPanel` expose `clear()`, `set_highlighted()` and one `sample_activated`. The window then calls the panel, not each chart.
